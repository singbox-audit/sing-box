# sing-box 公网代理服务端流量与 DNS 审计设计

## 1. 目标与运行环境

本系统用于一台运行 sing-box 的公网代理服务器。运维人员可以按时间、入站、账号、目标域名和出站组合查询历史流量，也可以逐条查看客户端 DNS 查询、响应和失败原因，并导出 CSV。第一版用 Hysteria 2（HY2）和 VLESS 两种认证入站验证多协议、多用户共存。

VPS 有 512 MB 可用内存、2 GB Swap 和 10 GB 可用磁盘。VPS 负责转发、采集和短期压缩缓存，本地电脑或 NAS 负责长期归档和分析。以下内容为设计与验收目标。接口以 sing-box v1.14.4 为基线，容量和性能需要在目标 VPS 上测量。

当前连接采集原型可用 `go build -tags with_quic ./cmd/sing-box` 构建，再用 `./sing-box run -c config.json --audit-directory /var/log/sb-audit` 运行。该参数启用普通 TCP/UDP 会话的开始与结束事件，省略时沿用上游行为。原型同步写入独立 zstd 帧，正常停机时把仍在跟踪的会话标记为中断。逐条 DNS、路由拒绝、周期快照、异步写入与归档恢复属于后续实施范围。

## 2. 转发与审计架构

基于固定版本构建审计版 sing-box，沿用官方 CLI、配置加载、协议注册和路由器。用户继续通过原版配置管理入站、出站、规则集、出站组和 DNS 服务器，按部署需要启用 Clash API 等管理接口。审计代码在原版处理路径上读取决定，避免在后台重新匹配规则或重新选择节点。

```text
认证入站（HY2、VLESS 等）
  └─ 原版连接路由
      ├─ route / 默认路由 → 连接 Tracker → 直连、代理或选定的组成员
      ├─ reject / 出站选择失败 → 记录决定或错误
      └─ hijack-dns → 内置 DNS 请求处理器 → 缓存或按 DNS 规则选用的公网解析器
               各采集点 ↓
      有界队列 → 流式 JSONL.zst → 按小时封卷
                                      ↓
                          本地归档 → DuckDB → CSV
```

### 2.1 用户归属与计量范围

连接和 DNS 事件共用三个字段：入站标签、入站协议、认证账号。默认用 `(inbound_tag, auth_user)` 标识账号。受审计入站应配置稳定的标签和非空、入口内唯一的账号名。同一客户端 IP 可以属于多个账号，同名账号也可以属于不同入口。确需跨协议汇总同一个人时，显式映射到稳定的 `account_id`，并保留事件发生时的原始身份。

HY2 和 VLESS 的 TCP/UDP 处理路径都会将已配置的用户名称写入入站上下文。后续接入 Trojan、TUIC、VMess 或多用户 Shadowsocks 时，逐一验证身份传递、支持的网络类型和关闭行为。受审计入口遇到空身份时保留原始事件并标记归属异常，避免按 IP 或凭据猜测用户。[HY2 入站](https://github.com/SagerNet/sing-box/blob/v1.14.4/protocol/hysteria2/inbound.go#L227-L270) · [VLESS 入站](https://github.com/SagerNet/sing-box/blob/v1.14.4/protocol/vless/inbound.go#L172-L203)

普通连接按已路由的 TCP 流或 UDP 会话记录。上传是从客户端读取的载荷字节，下载是向客户端写出的载荷字节，均以计数点实际处理的字节为准。统计范围不含外层代理封装与重传。QUIC/HTTP3 归入相应 UDP 会话，一个会话可以包含多个应用请求。

### 2.2 普通连接与出站分流

在路由器启动前通过 `AppendTracker` 挂载审计 Tracker。v1.14.4 的接口包含 `RoutedConnection`、`RoutedPacketConnection` 和 `RoutedFlow`。本设计的代理入站采集走前两条路径，复用上游的 TCP/UDP 计数包装器，按会话累计并只结算一次。连接开始时间取进入 Tracker 的时间。[接口定义](https://github.com/SagerNet/sing-box/blob/v1.14.4/adapter/router.go#L108-L112) · [上游计数实现](https://github.com/SagerNet/sing-box/blob/v1.14.4/common/trafficcontrol/tracker.go)

在回调中复制最终匹配规则、规则选中的出站和出站组当时展开的标签链。例如规则选中 `proxy`，选择链为 `[proxy, auto-jp, jp-02]`，本次转发交给 `jp-02`。一条连接只累计一次流量，报表可按策略或成员分别汇总。未命中显式规则时标记为默认路由，并记录实际选中的出站。这样手动切组或自动测速切换后仍能查询历史决定。[路由器实现](https://github.com/SagerNet/sing-box/blob/v1.14.4/route/route.go#L149-L198)

出站组选择链只描述原版路由器展开的组成员。出站自身的 `detour` 发生在拨号层。选择出站也早于拨号完成，只有观察到拨号结果时才能填写成功、失败或实际对端地址。路由拒绝、出站组无法选出支持当前网络类型的成员时，在对应路由分支记录结果和可用的身份、目标、规则信息，避免这些请求因未进入 Tracker 而消失。[路由分支](https://github.com/SagerNet/sing-box/blob/v1.14.4/route/route.go) · [拨号器实现](https://github.com/SagerNet/sing-box/blob/v1.14.4/common/dialer/dialer.go#L46-L65)

保留客户端提交的目标主机和端口。若路由配置会改写目标，在改写前取得原值。单独保存可观察到的 HTTP Host、TLS/QUIC Server Name 和实际目标 IP。嗅探未获得名称、或由远端代理解析目标时，相应字段留空。代理节点的 IP 不能填入目标站点 IP 字段。[协议嗅探能力](https://github.com/SagerNet/sing-box/blob/v1.14.4/docs/configuration/route/sniff.md)

### 2.3 客户端 DNS 逐条审计与解析器分流

部署策略由服务端决定上游解析器。将经受审计入口送达的明文 TCP/UDP DNS 通过原版 `hijack-dns` 路由动作交给内置处理器，规则放在会提前转发这些请求的规则之前。客户端本地完成的查询对 VPS 不可见。客户端经代理访问第三方 DoH、DoT 或 DoQ 时，服务端只能记录到解析器的普通连接。

可以先配置一个默认公网解析器。增加解析器后，`dns.rules` 可按 `domain_suffix` 或 `rule_set` 匹配查询域名，并通过 `route` 动作选择 DNS server 标签，其他查询使用 `dns.final`。客户端随后建立的业务连接由 `route.rules` 独立选择出站。需要配套时，两套规则可以引用同一份域名规则集。客户端直接提交目标域名让代理连接时，服务端为拨号执行的内部解析不计入客户端 DNS 查询数。[DNS 匹配规则](https://github.com/SagerNet/sing-box/blob/v1.14.4/docs/configuration/dns/rule.md) · [DNS 路由动作](https://github.com/SagerNet/sing-box/blob/v1.14.4/docs/configuration/dns/rule_action.md)

每收到并成功解码一条客户端 DNS 请求，就分配独立的 `request_id`，复制入站身份和问题，在调用解析器前记录开始事件。响应或错误返回后补充结果，并在客户端写回路径记录截断、写回长度或写回失败。缓存命中同样产生一条明细。客户端重新发送请求按新请求计数，服务端重试上游仍归于原请求。DNS 报文自身的 16 位 ID 会复用，不能用作归档主键。[TCP/UDP 请求与响应写回](https://github.com/SagerNet/sing-box/blob/v1.14.4/protocol/dns/handle.go)

DNS 日志记录规则选中的解析器标签；缓存状态和实际访问的上游从处理该次解析的路径获取，无法确定时留空。例如 20 条请求有 19 次命中缓存，查询报表仍应显示 20 条。解析结果与回写结果分别记录，`NXDOMAIN` 保留其响应码，超时且没有响应时响应码为空。答案按资源记录保存，以支持 A、AAAA、CNAME、HTTPS 等类型。

## 3. 事件与报表字段

所有时间统一为 UTC Unix 毫秒。流量计数使用 64 位整数。原始卷按连接与路由事件（`conn_*.jsonl.zst`）、DNS 事件（`dns_*.jsonl.zst`）分别保存。下表列出归档需能还原的字段，开始和结束事件通过同一个业务 ID 关联。

| 对象 | 主要字段 | 约定 |
| --- | --- | --- |
| 公共字段 | `event_time`、`event_type`、`inbound_tag`、`inbound_type`、`auth_user` | 写入时捕获身份。账号统一映射可在分析端完成 |
| 连接或路由决定 | `conn_id`、`seq`、`network`、请求主机和端口、嗅探域名、实际目标 IP、最终规则、所选出站、组选择链、处理结果 | ID 跨重启唯一。区分默认路由、拒绝、选择错误和交给出站。未观察到的结果留空 |
| 连接计量 | `conn_id`、`seq`、时间、累计上传和下载字节 | 开始、周期快照和结束共用 ID。结算时取最新有效的累计值 |
| DNS 请求 | `request_id`、接收和完成时间、`network`、查询名和类型、所选解析器、缓存状态、实际上游 | 按接收的请求计数，同一会话的并发请求分别关联 |
| DNS 结果 | `request_id`、`rcode`、响应答案、解析错误、截断标志、写回结果、上传和下载字节 | 答案反映为客户端编码的响应。TCP 计入 DNS 长度前缀，下载按实际写回字节计量 |

用户总载荷等于普通连接载荷加被接管 DNS 的载荷。后者绕过普通 Tracker，在 DNS 处理器单独计量。内部上游 DNS 流量不重复计入用户流量。按日分析长连接时，使用相邻快照的累计差值；跨日分配精度取决于快照间隔。

## 4. 写盘、故障恢复与归档

- **正常运行。** 事件经有界 Go Channel 交给后台写入器，直接流式压缩为 JSONL.zst。队列满时采用背压，记录队列水位和等待时间。磁盘满或写入失败时告警、保留未确认的数据并暂停接收新的受审计工作；故障持续时会影响转发。不得静默丢弃事件或自动删除尚未确认归档的卷。
- **异常中断。** 连接定期保存累计字节，DNS 分别保存接收和结束事件。每批完成独立可解压的 zstd 帧，再执行文件同步。重启后从未封卷文件恢复完整帧中的记录，隔离损坏尾部。只有开始或快照的记录标为中断并保留最后已恢复的值。尚在队列、压缩器或未持久化写入中的事件可能丢失；恢复窗口需连同排队时间实测。
- **轮转和退出。** 工作文件使用唯一卷名和 `.partial` 后缀，按小时轮转。封卷时完成压缩、同步和关闭，检查错误后在同一目录改名，再同步目录。正常停机先停止接入，等待在途 DNS 和连接结算，再排空队列并封卷。
- **传输和清理。** 本地用 rsync 拉取已封卷文件，也可用 rclone 复制到对象存储中转。校验文件内容并确认归档成功后，按卷删除 VPS 副本。同步失败可重试。本地按唯一卷名和校验值识别重复传输，并按连接序号或 DNS 请求 ID 与事件类型去重。
- **历史查询。** 保留原始压缩卷，用 DuckDB 转成按 UTC 日期分区的 Parquet。提供连接明细、每个请求一行的 DNS 明细，以及按用户、域名、出站汇总的视图，通过 SQL 导出 CSV。需要共享看板时再在本地部署 BI 服务。

## 5. 资源预算与验收

以原版同配置为基线测量开启审计后的进程 RSS、CPU、Swap 活动、转发吞吐、连接和 DNS 延迟，同时记录写入队列峰值、持久化延迟及每日压缩体积。负载应包括高并发短连接、持续下载、活跃长连接快照和大量含多条答案的 DNS 响应。根据峰值调节队列容量、快照周期、压缩参数和同步周期。

VPS 所需缓存约为“实测每日压缩体积 × 本地最长离线天数”，另留轮转、积压和恢复空间。例如测得 100 MB/天时，七天约需 700 MB，另加余量。根据 VPS 实际空闲空间设置预警和暂停接入阈值。

| 验收场景 | 核对结果 |
| --- | --- |
| HY2 和 VLESS 使用同名账号，从相同 IP 并发访问 | 入站与账号归属正确。仅显式映射后跨入口合并 |
| 极短 TCP/UDP、QUIC、已知双向载荷、半关闭、重复关闭 | 每个已路由会话结算一次，载荷与客户端测试数据一致 |
| 同配置分别运行原版和审计版，覆盖规则集、默认出站、嵌套组、切组、拒绝及选择失败 | 对比实际出口和处理结果。旧连接保留原选择，失败可定位到对应阶段 |
| 同一 UDP 会话重复查询、同一 TCP 会话并发查询、命中缓存、上游重试 | 与客户端逐条对账。用户查询数不随缓存或重试增减 |
| 两组域名分配给不同公网解析器，并设默认解析器 | 分别核对解析器收到的查询、客户端得到的答案和后续业务连接出口 |
| NXDOMAIN、超时、CNAME/HTTPS、多答案、UDP 截断和写回失败 | 查询原貌、响应码、答案和交付状态可区分，DNS 载荷只计一次 |
| 长连接跨日、优雅重启、强杀、磁盘写满、同步中断和重复导入 | 正常退出后对账一致；异常中断后可恢复完整帧、识别未完成请求、量出损失；重放不重复汇总 |

## 6. 实施与升级

1. 固定上游版本和构建特性，先用 HY2、VLESS、直连和一个代理出站组跑通身份、路由与 TCP/UDP 计量，再接入内置 DNS 请求和写回采集点。
2. 实现压缩写入、恢复和同步，在目标 VPS 上用 systemd 托管。执行上述功能与故障测试后，再确定可承受的峰值和离线保留天数。
3. 在本地完成 DuckDB 导入、去重、查询和 CSV 导出；用客户端已知流量和 DNS 请求清单对账。
4. 每次升级先核对 Tracker 接口、路由提前返回分支、出站组展开、DNS 缓存和写回路径，再使用原版同配置跑验收用例，通过后替换生产二进制。
